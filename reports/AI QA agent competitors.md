# Precision, not pointing, decides SQA's fate

The Jev thesis is mostly wrong, and the SQA experience already exists in two strong forms. Jev is not a computer-use model. It is a fast, very cheap model that answers yes/no and "pick one of these" questions. Its pointing feature ("Box") shipped two days ago as a preview. It has no published accuracy numbers, and TypeSafe itself says it is not production-ready. Meanwhile, Momentic's Mo already ships a "paste this into your coding agent" setup. It explores a live app with many agents, has a second agent reproduce each bug, and exports a report that a coding agent can fix from. Vercel's free `dogfood` skill targets "5-10 well-documented issues" with video, screenshots and repro steps, which is almost SQA's exact promise. The real problem in this market is not clicking. It is noise. Research benchmarks show that 65–85% of what AI testers flag is wrong. So SQA's only credible opening is to be measurably more precise than Mo and dogfood: about 5 bugs that are all real, re-checked in a fresh browser, with full evidence. The founder should prove that gap exists by running Mo, dogfood and Explorbot on one app before writing code.

## Jev answers small questions fast; it does not drive a browser

Jev is a "decision model" from TypeSafe AI, in early access since 15 September 2026. You give it text plus typed questions. It returns typed answers with probabilities: pick one option (Choice), rate on a scale (Score), or yes/no (Noul). It writes no prose and does not plan or act ([OpenRouter](https://openrouter.ai/blog/insights/what-is-jev/)). It is very cheap, at **about $0.04 per million input tokens, with output free** ([TypeSafe docs](https://docs.typesafe.ai/models)). It is fast, at **70–500 ms per call** ([InfoQ](https://www.infoq.com/news/2026/10/typesafe-ai-jev-released/)).

The pointing part of the thesis rests on Jev 1.14, announced on 14 October. It added image input and a "Box" answer that returns one rectangle as fractions of the image ([TypeSafe on X](https://x.com/typesafeai/status/2110536685805355064)). You can take the box centre as a click point. But the limits are serious. Every image request needs a header literally named `TypeSafe-Danger-Zone-Images`. Images are capped at **1,568 pixels per side** and are rejected, not resized, if larger ([TypeSafe images docs](https://docs.typesafe.ai/images)). Box **always returns a box, even when the target is not on screen**. There is no "not found" answer. The docs warn that small targets in large images get missed, and they label Box "Dreamer-ready", meaning it can change between releases ([TypeSafe Box docs](https://docs.typesafe.ai/primitives/box)). TypeSafe says images and Box "aren't yet up to our standards" for production ([madewithjev.com](https://madewithjev.com/jev-images)).

There are **no Jev results on any screen-pointing or computer-use benchmark** (ScreenSpot, OSWorld, WebArena). All of its published tests are on text tasks, such as sorting support tickets ([OpenRouter test](https://openrouter.ai/blog/tutorials/jev-vs-llm-when-to-use-each/)). For comparison, aggregator sites put frontier models at **roughly 85–93% on ScreenSpot-Pro**, a pointing test ([benchlm.ai](https://benchlm.ai/benchmarks/screenspot-pro)). Those figures are unverified, but they show that pointing is no longer the weak link it was. A popular "Jev computer use" demo does not even use Jev's eyes. Local software lists the screen elements, and Jev only picks one ([madewithjev.com](https://madewithjev.com/jev-images)).

The one real QA use of Jev today confirms this. Explorbot, an open-source testing agent, uses Jev to pick one element from a text list and to judge small yes/no questions. Those calls take **about 0.3 seconds instead of about 2.6 seconds** with a larger model. Explorbot only trusts answers above 70% confidence and falls back to the LLM otherwise. It does not use Jev for screenshots, planning or checking results ([Testomat blog](https://testomat.io/blog/deterministic-ai/)). There is also a safety warning. Security firm HiddenLayer reports that Jev is easier to fool than large LLMs. In a fake checkout page, a Jev-driven browser agent clicked an attacker's ad ([InfoWorld](https://www.infoworld.com/article/4236103/typesafe-ai-jev-even-more-susceptible-to-attack-than-llms-says-security-vendor.html)). That matters for a tool that explores other people's web pages.

The verdict on question one is this. Jev can make an SQA agent cheaper and faster on its many small decisions. It does not "unlock" automatic QA. Asking users for a Jev key adds setup friction for a part that is optional.

## Momentic Mo and Vercel's dogfood already deliver most of the experience

Two products cover most of what SQA promises. **Momentic Mo**, launched on 28 September 2026, is the closest paid match. Its quickstart contains a literal prompt to paste into the coding agent: "Help me set up Mo, Momentic's AI QA engineer, in this project." That prompt walks the agent through installing the `qa` CLI, logging in, installing skills, asking for the URL and test accounts, and starting a run ([Mo quickstart](https://momentic.ai/docs/mo/quickstart.md)). Mo sends a swarm of agents to explore. A **separate agent then retries each suspected bug from a clean browser**, and bugs it cannot reproduce are not filed ([Mo page](https://momentic.ai/mo)). The export gives each bug expected vs actual results, repro steps and a recording, in JSON a coding agent can read. After a fix, `qa send` asks Mo to rerun the original reproduction ([Mo reports](https://momentic.ai/docs/mo/reports.md)). Momentic has **$15M in Series A funding** and has shipped 49 versions of the CLI ([TechCrunch](https://techcrunch.com/2025/11/24/momentic-raises-15m-to-automate-software-testing); [npm](https://registry.npmjs.org/qa)).

Mo still falls short of the SQA promise in four ways. Its runs are **10–30+ minute swarms**, not one deep hour ([Mo quickstart](https://momentic.ai/docs/mo/quickstart.md)). It **returns every confirmed bug** rather than a curated top five. Its beta averaged about 3 verified bugs per run, and one customer reported 27 in an afternoon ([Mo launch](https://momentic.ai/blog/mo-launch); [Mo page](https://momentic.ai/mo)). Its tunnel for testing localhost is **in alpha** ([Mo tunneling](https://momentic.ai/docs/mo/tunneling.md)). Its report docs do not mention severity or console and network logs. You also still need a web dashboard step to get the API key, because the agent "cannot complete the browser sign-in" ([Momentic docs](https://momentic.ai/docs/core-concepts/agentic-testing)).

**Vercel's `dogfood` skill** is the free match, and it is the bigger threat to a paid product. One command installs it. Given only a URL, it logs in, maps the app, explores forms, modals, empty states and edge inputs, and writes each issue as it goes. Its stated target is "5-10 well-documented issues". Every interactive issue gets a repro video, a screenshot per step and an annotated result screenshot, and must reproduce on at least one retry ([dogfood SKILL.md](https://raw.githubusercontent.com/vercel-labs/agent-browser/main/skill-data/dogfood/SKILL.md)). It runs on agent-browser, which has **about 44k GitHub stars**, and the skill listing shows about 1.1M installs of the base skill ([agent-browser](https://github.com/vercel-labs/agent-browser); [skills.sh](https://skills.sh/vercel-labs/agent-browser/dogfood)). Its weaknesses are practical. It runs inside the developer's own agent, using their tokens and context. The same agent checks its own bug, in the same session. Results stay in a local folder.

The rest of the field is further away. The table compares the main options against the SQA promise.

## Most AI-reported bugs are wrong, so checking is the product

Independent evidence on bug-report quality is thin, but it points one way. On WebTestBench, a 2026 benchmark of 100 web apps with 448 real defects, leading models had **precision of only 25–35%**. That means two out of three flagged bugs were wrong. They also found only **17–33% of the real defects** ([arXiv 2603.25226](https://arxiv.org/html/2603.25226)). When the agents were handed a correct checklist of what to test, their scores **roughly doubled**. So the main weakness is knowing what to check, not how to click. On 120 real websites, the WebProber study found **85% of reported bugs were false positives**. Causes included misclicks, slow pages judged broken, and missing context, such as flagging a future conference year as a typo. Even so, a single pass found about 60% of the bugs humans had found ([arXiv 2509.05197](https://arxiv.org/html/2509.05197v1)). A mobile study found that running each test three times instead of once raised its score from **about 32% to about 49%** ([arXiv 2601.04500](https://arxiv.org/html/2601.04500)).

User reports match this. A hands-on review said TestSprite "generates numerous false positives" and burns credits on repeat runs ([DEV](https://dev.to/govinda_s/testsprite-review-ai-powered-testing-tool-promise-vs-reality-58k8)). One Hacker News tester said ScoutQA "didn't find any major problems" ([HN](https://news.ycombinator.com/item?id=45887738)). A developer who built her own bug-hunting agent found it "sometimes reported successes that never happened". She now files only high-confidence bugs with repro steps and a screenshot, and a second agent must reproduce each one before fixing it ([DEV](https://dev.to/debs_obrien/an-agent-that-hunts-bugs-in-my-app-while-i-sleep-2fe0)). Even Anthropic had three experts review each bug its testing agent found, and discarded any that one reviewer doubted ([Anthropic](https://www.anthropic.com/research/property-based-testing)). Long-standing research on bug reports says developers value accurate repro steps above everything else ([Bettenburg et al.](https://www.st.cs.uni-saarland.de/publications/files/bettenburg-tr-2007.pdf)).

The caveats are large. **No vendor publishes a false-positive rate, and no one has compared these tools head to head on the same app.** A planned independent comparison of Explorbot, Claude Code with Playwright and Mo has posted no results ([GitHub noisy-studio #154](https://github.com/noisy/noisy-studio/issues/154)). Reddit and G2 could not be reached for this research, so practitioner opinion is underrepresented. The practical takeaway is simple. At 25–35% precision, delivering 5 real bugs means finding about 15–20 candidates and then checking each one. That checking step is where an hour of run time should go.

## SQA's gaps are real but narrow, and Mo can close them fast

After Mo and dogfood, the open space is small. These gaps are left. A **curated, ranked top five** rather than every bug: no tool does this, and noise is the top complaint. A **re-check in a fresh browser by a different agent**: Mo does this, but dogfood does not. **Console and network logs** inside each bug report: Mo's docs do not mention them ([Mo reports](https://momentic.ai/docs/mo/reports.md)). A **one-command re-check of a single bug** after the fix: Mo's re-check runs through a chat message, and only ScoutQA has a per-issue command ([ScoutQA skill](https://awesome-copilot.github.com/skill/scoutqa-test/)). **Reliable localhost testing**: Mo's tunnel is alpha and TestSprite's CLI rejects localhost. **Running off the developer's context and tokens**: this is dogfood's weak spot, because long browser runs fill the agent's memory fast ([Playwright MCP](https://github.com/microsoft/playwright-mcp)). **Test accounts, one-time login codes and safe actions on live sites**: free tools just ask the user ([dogfood SKILL.md](https://raw.githubusercontent.com/vercel-labs/agent-browser/main/skill-data/dogfood/SKILL.md)). Finally, a **flat price per run**: Mo bills agent time plus model costs it does not publish ([Mo sessions](https://momentic.ai/docs/mo/sessions.md)).

The honest weakness is that each gap is a feature, not a moat. Mo is well funded, ships weekly and could add a "top 5" filter quickly. Skills like dogfood are plain markdown files that anyone can copy, so any prompt design SQA ships can be copied too ([dogfood](https://raw.githubusercontent.com/vercel-labs/agent-browser/main/skill-data/dogfood/SKILL.md)). Hacker News reactions to similar launches keep asking "why pay when my coding agent plus Playwright is free?" ([HN TesterArmy](https://hn.algolia.com/api/v1/items/48586299)). The one defensible claim would be a published, repeatable number, such as "5 of 5 bugs real, every time". No competitor has published one.

## Recommendation and a one-week hands-on test

Do not build SQA around Jev. Build it, if at all, around precision. Before writing code, test whether the precision gap is real. Run three tools on the same app, with the same one-hour budget, the same test account and the same short brief.

**Pick the app.** Use a staging app you own. Plant about 10 known bugs of mixed kinds: a form that accepts bad input, a save that fails silently, a broken link, an error shown only in the console, and a bug that needs three pages to trigger. Planted bugs let you measure what each tool missed, not just what it found.

| Tool | Why test it | Setup | Account you must create |
|---|---|---|---|
| **Momentic Mo** | Closest paid product; has independent reproduction | Paste the quickstart prompt into Claude Code; tunnel if local | Momentic account and API key ($250 free credits) |
| **Vercel dogfood** | Free baseline with SQA's exact output shape | `npx skills add vercel-labs/agent-browser --skill dogfood` | None beyond your coding-agent plan |
| **Explorbot with Jev on** | Built for long runs; shows what Jev adds in practice | `npx explorbot init --provider openrouter`, decision model `typesafe/jev-latest` | OpenRouter account and key (about $1/hour) |

| Measure | How to score it |
|---|---|
| **Confirmed bugs per hour** | Count a bug only if you can reproduce it from the report alone, in a fresh browser |
| **False-positive rate** | Wrong or unreproducible reports divided by all reports |
| **Planted bugs found** | Out of the 10 you seeded |
| **Cost per run** | Total dollars, including LLM tokens and credits |
| **Setup time** | Minutes from nothing to the first run starting |
| **Fix loop works** | Claude Code fixes the bug from the report alone, and the tool confirms the fix |

Add one half-day side test of the Jev thesis itself. Take about 50 screenshots of your app and name about 100 targets. Score how often Jev Box's centre lands inside the right element, and compare that with a frontier computer-use model on the same images. This also needs an OpenRouter or TypeSafe key.

Use a clear decision rule. If Mo or dogfood delivers about 4 or more confirmed bugs per hour with under 30% false positives, the gap is too small to build a company on. If all three are noisy, with more than half of reports wrong, or they miss most planted bugs, SQA has a real opening. Note that I could not run any of these tools. The founder has to create the Momentic and OpenRouter accounts and run the trials.

## Conclusion

The founder's thesis puts the hard problem in the wrong place. Clicking on the right pixel is largely solved by frontier models, and Jev's pointing is too new to trust. The unsolved problem is judgement: what to test, and whether a finding is real. Every benchmark shows that agents fail there first. That shifts the product, too. SQA's value is not "an agent that uses the browser". It is a guarantee that the bugs it hands back are real.

The market also changed under the idea in the last month. Mo launched in late September with the paste-a-prompt flow, and dogfood gives the same report format away for free. A new entrant can no longer win on the experience alone. It has to win on a number nobody has published yet: real bugs per hour at near-zero noise. The one-week test above is the cheapest way to learn whether that number is within reach.
